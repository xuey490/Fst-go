# FST 移动端技术选型评估（Android / iOS）

> 评估对象：在 Android 与 iOS 上实现与 PC 端一致的 mDNS 发现、加密通信（互认证）与文件传输。
> 评估基准：本仓库当前代码（go 1.26 / go-libp2p v0.50 / Wails v3.0.0-beta.29），2026-11。
> 结论基于代码事实与平台官方限制，不含未经验证的推测；估算工时为单人开发、含联调口径，误差约 ±40%。

---

## 0. 结论摘要

1. **可以实现，但不能按“原生 mTLS + 原生 mDNS + 原生 socket”的思路实现。** FST 的通信与发现都建立在 libp2p 之上，身份、加密、多路复用、协议协商是一整套语义；单独实现其中一层无法与现有 PC 端互通。
2. **推荐路线：复用 Go 核心，只换 UI 外壳。** 首选 `Wails3 + Vue3` 一套代码（移动支持目前为**实验性**），Android 先行；若 iOS 侧被 Wails 移动端能力卡住，退到 `gomobile + SwiftUI`，协议层零改动。
3. **明确否决**“用 Kotlin / Swift 重写 libp2p 协议栈”：jvm-libp2p 的 mDNS 与 circuit-relay-v2 仍是原型级（官方状态表标注未在生产验证），swift-libp2p 尚在 0.1.x；重写等于把最贵的部分重做一遍，且无法保证与 go-libp2p 的线级兼容。
4. **过渡方案**：`fst serve`（浏览器访问）是当月就能覆盖 iOS/Android“看和传”的最低成本路径，但它让手机**变成浏览器客户端**，手机本身不是 libp2p 节点，不满足“与 PC 相同”的定义。

| 路线 | 协议兼容 | 首次可用 | 主要风险 |
|---|---|---|---|
| A. Wails3 + Vue3 | 100%（同一 Go 核心） | 12–16 人周 | Wails 移动端实验性 |
| B. 原生 UI + gomobile | 100%（同一 Go 核心） | 20–26 人周 | 两套 UI、包体与构建链 |
| C. 原生重写 libp2p | < 60% 且不可控 | 40+ 人周，不封顶 | 发现/中继能力缺失 |
| D. fst serve（PWA） | 0%（手机不是节点） | 1–2 人周 | 需一台常驻节点 |

## 1. 先校准三个前提（对照代码）

### 1.1 “mTLS”在本项目里的真实含义

`internal/node/node.go` 只显式设置了 Identity、监听地址、ConnManager、ResourceManager、AutoNAT/打洞/中继，**没有覆盖安全传输**，因此走 go-libp2p 默认：**TLS 1.3 + Noise 双栈**。

| 维度 | 常规 mTLS | FST 实际做法 |
|---|---|---|
| 证书 | CA 签发 X.509 | 连接时自签，证书内嵌 libp2p 扩展，SAN 绑定 PeerID |
| 身份主键 | CN / SAN 域名 | Ed25519 PeerID（`identity.key`） |
| 双向认证 | 交换并校验证书链 | 双方校验“证书 ↔ PeerID”一致 |
| 密钥协商 | TLS | TLS 1.3 或 Noise XX |
| 应用层加密 | 无 | 无（明确不自研） |

含义：**互认证是满足的，但不是 PKI 意义上的 mTLS**。要在 Kotlin/Swift 里“只做 mTLS”并不能与 PC 互通——还必须实现 multistream-select 协商、yamux 多路复用、`/fst/msg` 等自定义协议，以及 `p2p-circuit` 地址语义。这正是路线 C 成本失控的根源。

### 1.2 mDNS 的服务名不是标准 DNS-SD 类型（关键发现）

```go
// internal/node/node.go
n.mdns = mdns.NewMdnsService(h, proto.MDNSService, n)   // proto.MDNSService = "fst"
```

go-libp2p 把该字符串原样交给 `libp2p/zeroconf`，后者不做补全（`newServiceRecord` 只拼 `service + "." + domain`）。因此实际广播/查询的是：

- **`fst.local.`**（TXT 记录 `dnsaddr=/ip4/.../tcp/8787/p2p/<PeerID>`）
- 而**不是**标准的 `_fst._tcp.local.`

后果很直接：

- iOS `NWBrowser` / Android `NsdManager` 要求合法类型 `_name._tcp`，**无法浏览裸标签 `fst.local.`**；
- iOS 的 `NSBonjourServices` 也必须填写合法类型，裸标签走不通审核与授权路径；
- 任何“原生 Bonjour 发现 + Go 节点连接”的混合方案，都必须先做**服务名标准化 + 双注册过渡**（见 §4.2）。

### 1.3 其他影响移动端的事实

- 单端口 8787，TCP + QUIC/UDP 同号，全部业务走 libp2p stream 多路复用。
- 文件字节不进前端，桌面端用“本地路径”传参；移动端没有可传的路径（见 §4.5），这是移植中改动最大的业务代码。
- `internal/bootstrap` 已把“与 UI 无关的装配”抽出（`Assemble`），但 `main.go` 尚未切换过去，`fst serve` 也还没有 CLI 入口——移动端若要复用装配逻辑，应先把这处收口。
- 跨网/代理能力由 `feature.WANUnlocked` 门禁，默认关闭。

## 2. 四条候选路线

### A. Wails3 + Vue3（同一 `main.go` 编到移动端）
Wails v3.0.0 已发布稳定版，官方支持 Windows/macOS/Linux，**Android 与 iOS 明确标注为实验性、不在稳定兼容契约内**；机制是 Go 编成 `libwails.so` / iOS 静态库，前端跑在系统 WebView，资源经 `wails://` 提供（不开本地端口）。

- 优点：一套 Vue 代码 + 一套 Go 核心；`bootstrap.Assemble`、事件总线、`/api/fst` 可原样复用；新增平台不改协议。
- 缺点：移动端实验性；WebView 在后台被挂起；大文件选择与保存要走平台桥；桌面 1280×800 布局必须重做为移动布局（“复用 UI”的实际收益比看上去小）。
- 现实前提：仓库当前是 `v3.0.0-beta.29`，且 `build/` 下无 Android/iOS 脚手架，需先升级并生成资产。

### B. 原生 UI + gomobile 绑定 Go 核心
Go 侧抽出一个 `mobile` 包（粗粒度 API：JSON 入参/出参或简单结构体），`gomobile bind` 产出 AAR（Kotlin）与 XCFramework（Swift），UI 用 Compose / SwiftUI。

- 优点：协议 100% 复用；系统集成最好（前台服务、分享扩展、SAF/Files、通知）；不受 Wails 移动端成熟度影响。
- 缺点：两套 UI、两套构建链；gomobile 的类型边界限制要求专门设计门面；包体增加；仍需自行处理 mDNS 权限与后台。
- 适用：团队有 Kotlin/Swift 人力，或产品要求“后台常驻接收、系统分享”。

### C. 纯原生重写 libp2p（Kotlin / Swift）
- jvm-libp2p：GossipSub 生产可用，但 **mDNS、circuit-relay-v2、AutoNAT 均标注为原型/未生产验证**，且官方声明“未听说有生产使用”。
- swift-libp2p：功能表覆盖较全，但版本仍在 0.1.x，依赖自定义 swift-tls/swift-quic；与 go-libp2p 的线级兼容需逐项验证。
- 结论：即使不考虑双份维护，**发现与跨网中继这两块恰是移动端最需要的部分**，而这正是两个实现最弱的部分。否决。

### D. fst serve（浏览器 / PWA）
复用同一份 UI，手机浏览器输入令牌即用；`internal/serve` 已实现 SSE + HttpOnly Cookie + multipart 上传。

- 优点：1–2 人周内可交付；不受商店审核与权限限制；平板体验尚可。
- 缺点：手机不是节点（无 mDNS、无本地直连）；必须有一台常驻节点；后台与通知能力弱；大文件受浏览器内存/磁盘策略约束。
- 定位：过渡与兜底，不作为“与 PC 相同”的答案。

## 4. 关键技术卡点（逐条给出对策）

### 4.1 iOS 的 mDNS 是硬门槛
Apple 文档明确：发送/接收组播、广播需要 `com.apple.developer.networking.multicast` entitlement；Bonjour 的注册/浏览/解析属于“本地网络操作”，需要 `NSLocalNetworkUsageDescription`，且 `NSBonjourServices` 必须声明服务类型；**应用在后台且权限状态未确定时，系统会直接拒绝且不弹窗**。

三条对策，按推荐度排序：

1. **改造服务名为标准类型** `_fst._tcp`，iOS 侧用 `NWBrowser` 浏览（多数情况下不需要 multicast entitlement，因为类型已在 Info.plist 声明），把发现的 `dnsaddr` TXT 注入 Go 侧 PeerStore，由 Go 建立连接。→ 需要协议兼容改造，但审核与权限路径最干净。
2. Go 侧继续用原始组播 socket，向 Apple 申请 multicast entitlement。→ 保留实现简单性，但审批周期与通过率不可控。
3. iOS 不依赖局域网发现，只走中继/DHT/手动添加。→ 可用，但与“与 PC 相同”有落差。

### 4.2 服务名标准化（桌面端也要改，但可向后兼容）
把 `proto.MDNSService` 从 `"fst"` 改为 `"_fst._tcp"`，并**同时注册旧名与新名、同时浏览两者**：老装机仍能被发现，新装机用标准类型。建议同时把 libp2p 默认的 `_p2p._udp` 一并浏览，便于与将来其他 libp2p 客户端互操作。这是一处必须在 P0 完成的前置改造。

### 4.3 Android 的权限与保活
- 原始组播需持有 `WifiManager.MulticastLock`（不持有则收不到 mDNS 响应）。
- Android 17 起本地网络访问进入 `NEARBY_DEVICES` 权限组，面向新目标 SDK 的应用默认被屏蔽（TCP/UDP/组播/`.local` 解析都受影响）；Google Play 要求 2027-08-31 后上架应用必须请求该权限。**现在就要把权限申请流程设计进去。**
- 持续传输需要前台服务（`dataSync` 类型 + 常驻通知），否则息屏后进程被回收。

### 4.4 QUIC 在移动网络上的不确定性
PC 端 TCP 与 QUIC 同端口并存。移动侧建议**先只启用 TCP**：运营商 CGNAT、企业 Wi-Fi、部分 iOS 网络策略会拦 UDP；而 libp2p 的协议协商与流语义与传输无关，只走 TCP 仍与 PC 完全互通。QUIC 作为后续优化，不作为首个版本的验收前提。

### 4.5 文件落盘抽象（改动量最大的业务代码）
现状：`transfer` 以本地路径为输入输出（`Send(paths)`、`LocalPath`、`.fstpart` 续传文件）。

移动端没有“任意可写路径”：

- Android：需要 SAF（`ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT`）或 `MediaStore.Downloads`，得到的是 URI / FD；
- iOS：`UIDocumentPicker` + App 沙盒 + Files 共享，写入需 `startAccessingSecurityScopedResource`。

对策：在 `transfer` 内引入最小抽象——**发送侧 `source`（可 ReadSeeker）与接收侧 `sink`（可 Write/Truncate/Seek）**，桌面实现仍是文件路径，移动实现走 FD/URI 流。`.fstpart` 断点续传语义保持不变（续传依赖的 offset 与 SHA-256 校验逻辑可完全复用）。

### 4.6 后台传输与“在线”语义
iOS 后台执行窗口以秒计（`beginBackgroundTask` 约 30s），大文件无法在后台完成；Android 靠前台服务可较长驻留。产品上需要接受：

- “在线”从“常驻在线”变为“前台在线 / 后台仅保活短时”；
- 大文件必须前台传输，或依赖已有的断点续传在回到前台后继续；
- 离线消息队列（`queued` + 指数退避）在移动端反而是优势，可直接复用。

### 4.7 通知与系统分享
- Android：`Share Intent` 接收文件 → 落临时目录 → 走既有 `Send`；需要 `FileProvider`。
- iOS：`Share Extension` 是独立 target，Go 核心不能简单复用主 App 进程；建议扩展只做“写入 App Group 暂存 + 拉起主 App 发送”，避免在扩展里跑 libp2p。

### 4.8 TUN 代理：建议移动端不做
Android 可用 `VpnService`（需对所有 libp2p socket 调 `protect(fd)` 防环回，工作量不小）；iOS 需 `NEPacketTunnelProvider` 与专门 entitlement，审核严格。移动端定位为“聊天 + 传输”，代理留在桌面与中继侧。

### 4.9 包体与性能
libp2p + kad-dht + quic-go + SQLite 的静态库会显著增加包体（AAR/XCFramework 原始体积约 40–70MB 量级，按 ABI 拆分后单 ABI 明显更小）。现代 WebView 的内存与启动开销在移动端可接受，但**不要期待桌面级的冷启动与常驻内存**。

## 5. 判定：哪个更好

按目标拆开回答，避免“一刀切”：

| 你的优先级 | 推荐 |
|---|---|
| 最快让手机与 PC 互传互聊，且只有一个人维护 | **A（Wails3 + Vue3）**，Android 先行 |
| 要后台常驻收文件、系统分享、原生手感、上架质量 | **B（原生 UI + gomobile）** |
| 只是想让手机能看/能传，不想做客户端 | **D（fst serve）** 先顶住 |
| 想“用 Kotlin/Swift 从头做一套” | **不做**（C） |

**推荐组合（本文主张）**：以 A 为主线，B 作为逃生舱，D 作为过渡；三者共用同一个 Go 核心与同一份协议，任何时刻切换只换外壳，不换协议。这样选型的最大风险不是“选错栈”，而是“协议被改坏”——所以先把 §4.2、§4.5 两处改造做掉，后续无论走 A 还是 B 都不返工。

## 6. 分期实施计划

### P0 协议与核心可移植化（1–2 周，桌面端先行）
1. mDNS 服务名标准化 + 双注册/双浏览（向后兼容）。
2. `transfer` 引入 `source`/`sink` 抽象，桌面实现保持路径不变。
3. 收口启动装配：`main.go` 切到 `bootstrap.Assemble`，补 `serve` 子命令（同时修复 README 与实现不一致）。
4. 抽出 `internal/mobile` 门面包（粗粒度 API + JSON 或简单结构体），供 gomobile 与 Wails 两种形态共用。

**验收**：桌面 ↔ 桌面发现、聊天、1GB 断点续传、群聊全部回归通过；`go test ./internal/...` 全绿。

### P1 Android（4–6 周）
- 首选 Wails3 移动端；若生命周期/文件桥受阻，改 gomobile + Compose（协议层不变）。
- 必做：MulticastLock、Android 17 本地网络权限适配、前台服务、SAF 落盘、通知。
- **验收**：同 Wi-Fi 发现 ≤5s；文本/图片/文件互通；1GB 文件断点续传；息屏前台服务下持续传输 30 分钟；跨网经中继互通；群聊收发正常。

### P2 iOS（4–6 周）
- 取决于 4.1 的 Spike 结果：优先走“标准服务名 + NWBrowser”，否则申请 multicast entitlement。
- 必做：本地网络授权流程、`UIDocumentPicker` 落盘、前台传输与恢复、后台挂起提示。
- **验收**：真实设备（非模拟器）授权后可发现 PC；1GB 前台传输成功；切后台再回前台可续传；拒绝本地网络权限时给出可操作提示。

### P3 打磨（按需）
分享扩展、通知中心、平板双栏布局、深色模式、崩溃与日志上报（本地文件即可）。

## 8. 先做三个 Spike（每个 1–2 天，花小钱排大雷）

1. **S1（iOS 组播）**：最小 Go 程序在真机上注册/浏览 mDNS，观察是否被系统拒绝 → 决定走 entitlement 还是 NWBrowser。
2. **S2（Android 全链路）**：Wails3 移动端跑通 FST 核心，发现 PC 并传 100MB → 验证实验性支持的可用边界。
3. **S3（落盘吞吐）**：SAF / UIDocumentPicker 写入 1GB，测吞吐、内存峰值与续传恢复 → 验证 §4.5 抽象是否足够。

三个 Spike 全部通过再进入 P1；任一失败，按 §5 的逃生舱切换，不影响协议层。

## 9. 明确不要做

- 不要为移动端新开业务端口（保持 8787 单端口与 stream 多路复用）。
- 不要在 Kotlin/Swift 侧“只做 mTLS”然后自研消息格式。
- 不要把文件字节读进 WebView 再上传。
- 不要在 iOS 后台假设长连接可用。
- 不要把 TUN 代理作为移动端首发功能。
