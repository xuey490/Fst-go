# 局域网发现排查报告：为什么只有一台 PC 能看到手机

- 时间：2026-11-09
- 现场：开发机 `DESKTOP-PQ5PGJI` / 192.168.1.15、另一台 PC `DESKTOP-76VRP96` / 192.168.1.24、手机 Xiaomi 2312DRA50C / 192.168.1.13
- 现象：只有开发机显示手机；手机端也只显示开发机；另一台 PC 两边都看不到对方手机
- 结论：**不是握手、加密或协议不匹配，是两个纯发现层问题**（mDNS 服务标签断层 + 手机 mdnsd 不应答查询）

## 1. 证据（抓包，不是推测）

用 `cmd/mdnssniff`（IPv4 组播 224.0.0.251:5353，主动发 PTR 查询）与 `cmd/mdns6`（IPv6 ff02::fb）分别抓了 12–40 秒：

| 观察 | 原始记录 |
|---|---|
| 另一台 PC 只广播历史标签 | `PTR fst.local. -> FST-12D3KooWSoXaZo8hPt8EWGXdagpNV4NBXfySjqsRkAE1Dmz3eVVV.fst.local.`，**没有任何 `_fst._tcp.local.` 记录** |
| 该 PC 仍在用旧版逻辑 | TXT 里带 `dnsaddr=/ip4/172.19.224.1/...`（WSL/Hyper-V 虚拟网卡）；新版 `suitable()` 已过滤回环/链路本地/中继，且不会漏掉这种多网卡垃圾地址 |
| 开发机（新版）双注册 | 同时出现 `PTR _fst._tcp.local.` 与 `PTR fst.local.`，A 记录只有 `192.168.1.15` |
| 手机有一段时期**完全不应答** | 连续 3 次抓包里来自 192.168.1.13 的报文只有系统 Fast Pair 的 `_lyra-mdns._udp.local.` 查询（源端口 47142），5353 上零记录；带 QU 位的查询同样无应答 |
| 手机并没有掉线 | 同期 `netstat` 显示 `192.168.1.15:8787 <-> 192.168.1.13:8787 ESTABLISHED`，核心端口可连 |
| 之后手机恢复应答 | 21:05 抓到 `RESP from 192.168.1.13:5353`：`PTR _fst._tcp.local. -> FST-12D3KooWFSDwX...`，但实例名带 ` (2)` 后缀（见第 4 节） |

**推论：** 开发机能「看到」手机，靠的不是自己发现，而是手机主动拨进来之后的对端记录；另一台 PC 看不到手机，是因为它压根不浏览 `_fst._tcp`，而手机又只注册这个标准名。

## 2. 根因

### 根因 A：两代客户端用的 mDNS 标签不一样（确定，可复现）

| 角色 | 注册（对外广播） | 浏览（找别人） |
|---|---|---|
| P0 之前的桌面端（现场另一台 PC） | `fst.local.`（裸标签，非法服务类型） | `fst.local.` |
| 新版桌面端 | `_fst._tcp.local.` **+** `fst.local.` | `_fst._tcp.local.` **+** `fst.local.` |
| 手机（Android `NsdManager`） | `_fst._tcp.local.`（**只能**用标准名） | `_fst._tcp.local.` |

于是出现两个方向的单向不可见：

- 旧 PC → 手机：旧 PC 只查 `fst.local.`，手机不在这个标签上 → 看不见；
- 手机 → 旧 PC：手机只查 `_fst._tcp`，旧 PC 不在这个标签上 → 手机列表里只有开发机。

这就是截图里「手机设备页只有 1 台」和「另一台 PC 设备页只有 1 台」的直接原因。

### 根因 B：手机的系统 `mdnsd` 会间歇性不应答组播查询（现场复现）

手机核心在跑、TCP 连通，但连续三分钟抓不到它任何 5353 报文，也不回应 PTR 查询。这是 Android 侧现象（息屏/省电时组播收包被掐、或 `mdnsd` 处于挂起态），应用层拿不到错误码。

后果：即使双方标签一致，PC 也发现不了手机——因为**发现依赖「对端回应我的查询」**，而手机不回。反过来手机能看见 PC，是因为 Android 的查询带 QU 位、PC 单播回应。

### 根因 C：多网卡机器上组播出口选错（另一台 PC 的启动日志）

另一台 PC 的日志里刷满：

```
[WARN] mdns: Failed to set multicast interface: setsockopt: An invalid argument was supplied.
```

它同时开着 4 个带 IPv4 的网卡：`192.168.1.24`（真实局域网）、`172.19.224.1`（WSL/Hyper-V）、`169.254.114.26` 与 `169.254.171.193`（APIPA，没有 DHCP）。`zeroconf` 在 Windows 上每发一个报文都要逐网卡 `SetMulticastInterface`，遇到没有可用单播地址的网卡就是 `WSAEINVAL`；更麻烦的是失败后报文会从「上一次设置成功」的网卡发出——完全可能从 WSL/APIPA 网卡出去，**局域网里没有任何设备收得到**。

于是这台 PC 既能广播出自己（我们抓包能看到它的记录，但 TXT 里混着 `172.19.224.1`），又极不稳定地收到别人的记录。

## 3. 修复

### 3.1 桌面端：发现代理（代播）

`internal/lanmdns` 新增 `Bridge` / `Unbridge`：

- 发现或连上某个对端后，把它**补播到对方自己没有广播的标签**上：
  - 手机（只会 `_fst._tcp`）→ 由桌面端在 `fst.local.` 上代播，旧 PC 立刻可见；
  - 旧 PC（只会 `fst.local.`）→ 由桌面端在 `_fst._tcp` 上代播，手机立刻可见。
- 只知道「它连上了我」而不知道它用什么标签时，**只往历史标签补**。抢注标准名会触发 DNS-SD 重名检测，把手机自己的实例改名成 `FST-xxx (2)`（现场抓到过），因此不能这么干。
- 代播实例名带 `-br` 后缀（`FST-<PeerID>-br`），用来把「本机代播的记录」和「对端自己的记录」区分开（否则会把本机代播当成对端自播，撤销注册形成自毁循环）。
- **别人代播的记录必须收下（2026-11-09 的第二个关键修复）**：`-br` 后缀不等于「忽略」。收到 `-br` 记录时只判断归属——
  - 实例名里的 PeerID 就是本机 → 自己播出去又被自己浏览回来的，丢掉；
  - PeerID 是别人 → **这是中转机牵的线，必须当成一次正常发现派发**，只是不参与代播决策（否则多台中转机会互相代播形成回环）。
  现场证据：`192.168.1.24` 上 `mdnsview` 只看到
  `service=fst instance=FST-<手机 PeerID>-br ipv4=192.168.1.13`，没有手机的自播记录；
  旧实现无条件丢弃所有 `-br`，于是这台 PC 永远只认识开发机。修复后日志出现
  `msg="mdns discovered" ... via=bridge`，对端随即被拨号。

- 以 PeerID 为键、随发现/连接刷新；对端断开即 `Unbridge`；闲置 20 分钟由巡检协程清掉，避免幽灵设备。
- `internal/node`：`onConnected` 调 `bridgePeer`（只取私网/回环且非 `/p2p-circuit` 的地址），`onDisconnected` 调 `Unbridge`。

### 3.1.1 桌面端：只让真实局域网网卡参与组播

`lanmdns.LANInterfaces()` 逐条过滤，任一不满足即剔除：

1. 已启用（`FlagUp`）且支持组播（`FlagMulticast`）；
2. 非回环；
3. 至少有一个可路由 IPv4（排除 `169.254.x` 这类没有 DHCP 时的自动地址）；
4. **真实探测** `setsockopt(IP_MULTICAST_IF)` 成功（`probeMulticastIPv4/6`）。

第 4 条是关键：前 3 条只能保证「地址看起来对」，而系统仍可能拒绝把某块网卡
当作组播出口，`zeroconf` 随后对每个报文打印一次 `Failed to set multicast
interface`，并且报文会从别的网卡发出。

排序与载荷同步收紧：

- `primaryIPv4()` 用一次 UDP connect 让系统选路，`LocalAddr` 即默认路由所在网卡，
  `ifaceRank` 给它最高分，保证 `192.168.1.24` 排在 `172.19.224.1` 前面；
- `buildPayload` 的 `allowed` 只取排序后的第一块网卡，TXT/A 记录里不再出现
  对端拨不到的 `172.19.x`、`169.254.x`；
- 环境变量 `FST_MDNS_IFACE=<名字或序号>`（逗号分隔）可强制指定，用于自动挑选
  仍不对的现场。

启动日志会写出决策结果：

```
msg="fst started" version=0.1.0 build=2026-11-09-mdns-iface-probe
msg="mdns interfaces" selected="[以太网#10=192.168.1.15]" ipv6_multicast=true hint="..."
```

现场效果：同一个二进制在本机启动后，`Failed to set multicast interface` 从
「每毫秒数条」变成 **0 条**；`bin/netdiag.exe` 可单独跑，逐块网卡给出
`MCAST_V4` / `MCAST_V6` 探测结果与 `SELECTED` 状态，`FAIL` 的那块就是告警来源。

### 3.1.2 现场复现：Hyper-V 虚拟网卡混进了 mDNS 网卡列表

异常 PC 的 `ipconfig`：

```
无线局域网适配器 WLAN:            192.168.1.24 / 255.255.255.0 / 网关 192.168.1.1
以太网适配器 vEthernet (Default Switch): 172.19.224.1 / 255.255.240.0
无线局域网适配器 本地连接* 9 / * 10:     媒体已断开连接（Wi-Fi Direct 虚拟适配器）
```

`vEthernet (Default Switch)` 是 Hyper-V 的内部 NAT 交换机，它有合法私网 IPv4，
所以「有可路由 IPv4」这一条它完全通过；但它并不连到局域网，`zeroconf` 每发
一个报文都会对它执行一次 `SetMulticastInterface`，系统返回
`WSAEINVAL` → 就是那串 `[WARN] mdns: Failed to set multicast interface`。
更糟的是失败后报文会从「上一次设置成功」的网卡发出，等于把 mDNS 出口交给了
虚拟交换机。

因此 3.1.1 的「按地址筛选」不够，必须是**真实探测 + 默认路由优先**：

| 步骤 | 实现 | 作用 |
|---|---|---|
| 真实探测 | `probeMulticastIPv4/6` 在临时 socket 上真的调用一次 `SetMulticastInterface` | 探测失败的网卡直接剔除，告警根治 |
| 默认路由优先 | `primaryIPv4()` 用 UDP connect 让系统选路，取 `LocalAddr`；`ifaceRank` 给它最高分 | 保证 `192.168.1.24` 排在 `172.19.224.1` 前面 |
| 只广播首选网卡 | `buildPayload` 的 `allowed` 只取排序后的第一块网卡 | TXT/A 记录里不再出现对端拨不到的 `172.19.x` |
| 人工兜底 | 环境变量 `FST_MDNS_IFACE=<名字或序号>` | 自动挑选仍不对时一次定位 |

启动日志会明确写出决策结果，现场不必再猜：

```
msg="fst started" version=0.1.0 build=2026-11-09-mdns-single-egress
msg="mdns interfaces" selected="[WLAN#5=192.168.1.24]" ipv6_multicast=false hint="..."
```

`bin/netdiag.exe` 可以单独跑，逐块网卡给出 `MCAST_V4` / `MCAST_V6` 探测结果与
`SELECTED` 状态——`FAIL` 的那块就是告警来源。

### 3.1.2.1 为什么还要「虚拟网卡剔除 + 单出口收敛」

3.1.2 的探测没能根治现场那台机器：它的新日志里

```
msg="mdns interfaces" selected="[WLAN#5=192.168.1.24 vEthernet (Default Switch)#25=172.19.224.1]"
[WARN] mdns: Failed to set multicast interface: setsockopt: An invalid argument was supplied.
```

`vEthernet` 的临时探测居然通过了，但 `zeroconf` 真正发报文时仍然失败。原因是
`zeroconf` 在 Windows 上**逐网卡**执行 `setsockopt(IP_MULTICAST_IF)` 再发送：
列表里只要有一块网卡被系统拒绝，每发一个报文就打印一次 WARN，而且报文出口
取决于「上一次设置成功的那块网卡」，完全不可控。

所以再加两条规则（`LANInterfaces`）：

| 规则 | 实现 | 为什么 |
|---|---|---|
| 剔除虚拟网卡 | `isVirtualIface` + `dropVirtual`，匹配 `vEthernet`/`VMnet`/`VirtualBox`/`docker`/`tun`/`wg` 等名字；**仅当本机还有物理网卡时**生效 | 虚拟交换机不连局域网，既产告警又发错地方；全虚拟环境仍保留原列表，不会把 mDNS 关掉 |
| 单出口收敛 | 排序后若首选是「默认路由 + 物理网卡」且还有其他候选，只保留它，并打 `mdns egress pinned` | 出口唯一确定；多一块网卡就多一份告警风险。真需要多网卡（两张物理网卡接不同局域网）时用 `FST_MDNS_IFACE=网卡1,网卡2` |

同一批次还把代播的重复注册去掉了：`bridge` 只在「端口/主机名/A 记录」变化时
重建记录，TXT 变多（peerstore 补上 quic 地址）不再触发撤销重播——现场日志里
同一个对端连续两条 `mdns bridged peer` 就是它造成的。

### 3.1.3 一个容易误判的坑：单实例接管

桌面端启用了 Wails 单实例（`UniqueID=com.fst.app`）。**旧进程还在托盘里时，
双击新 exe 只会把窗口交给旧进程、新进程随即退出**——用户看到窗口弹出来，
以为新版已经生效，实际上跑的还是旧代码。

判别方法：日志里出现下面这行，就说明这次启动被旧进程接管了，必须先从托盘
退出（或结束进程）再启动：

```
msg="second launch handed off to the running instance; quit it before running a new build"
```

### 3.2 现场二次复现：这次真不是 mDNS，是二层不通

修完代播记录过滤后，`192.168.1.24` 的日志已经出现

```
msg="mdns discovered" peer=12D3KooWKjMj… service=fst.local. addrs=[/ip4/192.168.1.13/tcp/8787] via=bridge
```

即「手机地址已经拿到」，但界面里仍然只有开发机。原因是**设备列表要收到 HELLO 才落库**（`node.learn` → `Store.UpsertPeer`），中间还有一步 `dial`。在该机跑 `probe.ps1` 得到：

| 目标 | ping | TCP 8787 | ARP 表 |
|---|---|---|---|
| 192.168.1.13（手机，无线） | **False** | **TIMEOUT 4s** | **无条目** |
| 192.168.1.15（开发机，有线） | True | OK | `30-9c-23-cd-04-93` |
| 192.168.1.1（网关） | True | – | – |

开发机对同一个 `192.168.1.13:8787` ping 通、TCP 通，说明手机侧一切正常。**`arp -a` 里根本没有 192.168.1.13**，等于二层地址都解析不出来 —— 这是「无线↔无线被拦、无线↔有线放行」的典型表现，也就是 AP/路由器开着**客户端隔离（AP isolation / 无线设备隔离）**，或手机连在访客网络/另一台做了隔离的 AP 上。

这类问题代码无法解决：组播被拦只是它的一半，TCP 同样被拦。正确做法是关掉路由器里的「AP 隔离 / 客户端隔离 / 访客网络」，或把这台 PC 改接网线。

判别口诀：**`mdns discovered` 有了但设备不出现 → 一定卡在 `dial`**；`dial failed` 的 `err` 是 `i/o timeout` 就是丢包（隔离/防火墙），`connection refused` 才是端口问题。

**现场验证（闭环）**：把这台 PC 的 Wi-Fi 关掉、改接网线后，手机立即出现，无需改动任何代码或环境变量。这印证了故障点在二层：AP 只在**无线客户端之间**做隔离，无线口与有线口之间的流量走 AP 内部桥接，不受该策略限制。所以同一条链路上「有线↔无线通、无线↔无线不通」不是巧合，而是隔离策略的作用范围。

### 3.3 手机端：周期重播 + 状态可见

- `Nsd.announceAgain()`：注销后 400ms 重注册，等于主动广播一次。`FstRepository` 每 3 分钟调一次（`REANNOUNCE_MS`），不依赖「能否收到组播查询」。
- 注册失败自动 15 秒重试（`RETRY_DELAY_MS`），并把 `code=N` 显示出来。
- 状态条新增一行「广播：已注册 / 注册失败（code=N）」，这是「别人能不能看见我」的唯一判据。
- 版本：`versionCode 5` / `0.1.4`。

## 4. 验证

1. 单测：`go test ./internal/lanmdns`（新增 `bridgeParts` / `bridgeTargets` / `markAdvertised` / `equalStrings` 四组断言，全绿）。
2. 双节点实测（`FST_PORT=18787 FST_DATA_DIR=… fst serve`），日志：
   - `mdns bridged peer peer=12D3KooWSoXaZ… service=_fst._tcp.local. ip=[192.168.1.24]` —— 把旧 PC 补播到标准标签，手机能看见它了；
   - `mdns bridged peer peer=12D3KooWFSDwX… service=fst.local. ip=[192.168.1.13]` —— 把手机补播到旧标签，旧 PC 能看见它了。
3. 模拟端验证：`cmd/mdnsfake`（只注册 `_fst._tcp` 的假移动端）启动后 5 秒内被代播到 `fst.local.`，抓包可见 `PTR fst.local. -> FST-<假PeerID>.fst.local.`。
4. 稳定性：同一 PeerID 的服务类型只注册一次（早先因地址顺序不同会反复重建，已用排序修正）；代播实例名加 `-br` 后缀后，本机不会再把自己播出去的记录当成「对端自播」而撤掉（原先存在创建→撤销的自毁循环）。
5. 组播告警：新版本启动后日志里 `Failed to set multicast interface` 计数为 0（旧版本在同一台机器上每毫秒数条）；本机与异常 PC 同款网卡结构（真实网卡 + 虚拟交换机）下，虚拟网卡会被探测剔除。
6. 可观察性：启动日志新增 `fst started build=...`、`mdns interfaces selected=[...]`；被旧进程接管时旧进程会写 `second launch handed off ...`，三种状态可以直接从日志区分。

### 4.1 两个地址格式为什么不一样

| 来源 | 形态 | 说明 |
|---|---|---|
| 手机 `/self`、界面显示的监听地址 | `/ip4/192.168.1.13/tcp/8787`、`/ip4/192.168.1.13/udp/8787/quic-v1` | libp2p 的**监听地址**，本来就不带 `/p2p/`（PeerID 由连接握手交换） |
| 桌面端日志 `node started addrs=` | `/ip4/192.168.1.15/tcp/8787/p2p/12D3KooW…` | 同一份地址加上 `/p2p/<PeerID>` 的**可拨号地址** |
| 手机写进 mDNS TXT 的内容 | `dnsaddr=/ip4/192.168.1.13/tcp/8787/p2p/12D3KooW…` | 也是带 `/p2p/` 的完整可拨号地址 |

也就是说两端在发现层交换的都是「带 `/p2p/` 的可拨号地址」，**不存在协议不一致**；截图里那条不带 `/p2p/` 的是 /self 的监听地址展示，不是广播内容。

## 5. 现场怎么用

1. **所有 PC 都换成新 `bin/fst.exe`**（旧版不认识 `_fst._tcp`，只能被动受益于代播）。
2. 手机装 `phone/dist/fst-0.1.4-arm64-debug.apk`。
3. 看三处状态即可定位问题：
   - 手机状态条「广播：已注册」= 手机在对外广播；若是「注册失败（code=N）」则别人一定看不到它。
   - 桌面端日志 `msg="fst started" ... build=2026-11-09-mdns-single-egress` = 跑的是这一版（旧进程在托盘时会被单实例接管，见 3.1.3）。
   - 桌面端日志 `msg="mdns interfaces" selected="[WLAN#5=192.168.1.24]"` = 只用了 WiFi；
     若这里出现两块以上网卡，看紧跟的 `mdns egress pinned` / `mdns interfaces skipped` 说明原因。
     之后整份日志里 `Failed to set multicast interface` 应为 **0 条**。
   - 桌面端日志出现 `mdns registered service=_fst._tcp.local.` 与 `service=fst.local.` 两行 = 双注册正常；只有一行就是旧版。
4. 只要局域网里有一台新桌面端在线，手机与旧 PC 之间也能互相发现（代播），不必逐台升级。

## 6. 已知限制

- 跨子网/跨 VLAN 不生效：mDNS 不出路由器，代播同样依赖组播可达。这种场景请在中继/`目录`模式下手动添加设备。
- 代播是「别人替你说话」，对端离网后最长 20 分钟才会撤销（连接断开时会立刻撤销）。
- 组播只在「有可路由 IPv4 的网卡」上进行；纯 IPv6 组网（无 IPv4）会回退到库的默认行为，此时仍可能出现上述告警。
- 手机 `mdnsd` 挂起属于系统行为，只能靠周期重播兜底；如果某台 ROM 连主动重播都拦（极少数），需要换用「手动输入 IP/扫码」入口。
